Data and information management

The longest page here, and the one worth your time. Everything else in this resource assumes the idea on this page: that a fact captured properly once can be used everywhere, and a fact typed into a cell cannot.

On this page

Data, information, and why the difference costs money

Data refers to a bunch of facts collected and stored. Raw data does not mean anything on its own. That is why data has to be processed. Information is the result of how data is processed. Data can be manipulated, mined, or processed to become valuable information. This is done with smart algorithms, data mining, and some human guidance to find valuable patterns in the data. In a dataset the raw value “12” could be stored. This means nothing on its own. Taking it in context: information -> 12 meters of 20mm polycop sold on 12 October 2026. This information does not mean that much. That is why knowledge needs to be applied. This information needs to be used to make valuable, best decisions in the scenario.

In this context it could mean Lerato hardware and home should order more stock before 20 October 2026 otherwise they would run out of stock.

A row versus a record

So a row would be a horizontal line on a spreadsheet. A record would be a complete set of related information about a specific thing, like a product, a customer or an invoice. Although a row can represent a record, a record is more than the values you just see in the table. It also needs context and information that can be understood and trusted later.

A record would have two parts the actual business data and the envelope of the metadata. The business data would contain useless, useful facts like a product name, price, stock and quantity, the envelope stored in the meta blocks carries information about the data itself. Metadata would be your data about your data. It would help explain things like where did the information come from, who captured it, when it was recorded, which version of the application was used to view this data or to store this data.

What this would mean at Lerauto Hardware and Home would be that if information is stored in a spreadsheet, the row would be the actual Row inside of the spreadsheet where the data is stored like the price, the quantity, description, the product name and the metadata could be Sales per season of the yearOr anything useful and meaningful that could be stored about the data additionally without needing to recapture some more information.

Using a spreadsheet would still be valuable. It is excellent for quick calculations and exploring figures and building a quick analysis about your information. Excel is not the problem, the problem would be to rely on a spreadsheet as a database. A spreadsheet cannot be a database, it is just a quick analysis or capturing of data or calculation that could be done. Excel should not be excluded from the business idea, it should be used efficiently for its purpose as well as databases used efficiently for its purpose.

If we would take a look at our records, it would appear that half of the information would be a waste, but it would serve a purpose. Some of the data stored could look meaningless, but using metadata we can extract valuable information out of all of these data stored.

This would store a lot of context that could be used to make meaningful decisions. These records don’t provide any meaning outside of the context, It could be regarded as unnecessary paperwork, but it would make all of the information and conclusions with the data trustworthy.

A Schema of the shop would determine how a record would look and contain what field names.

Examples of this could be if there is a needed customer ID as well as contact details and maybe other agreed fields. Writing this definition would determine a lot of things like validation checks, ranges, storage, and a bunch of set of rules for the business that can be implemented inside of the data fields.

Structured data would Distinguish between master data and your transactional data. Master data describes something that already exists, like a customer, product and suppliers. If a customer’s phone number is incorrect, the customer record can’t be corrected.

Transaction data describes things that happens such as sales and stock movement. Once a transaction has been recorded, it should not be edited or deleted to hide a mistake, since the delta mostly follow-ups and used for valuable information. Inaccurate data would cause problems. That is why it is so important to validate the input and ensure once data is captured it cannot be edited or deleted for transacational data.

Information quality: six questions, one score

"Is the data good?" is too vague to act on. These six questions are not. Each one is a check a system can run by itself, and each one is currently failing somewhere in the shop's records.

Each example is a real failure in the demonstration data set, taken from the migrated spreadsheet.

Information quality would describe how suitable information is for the job and what it needs to do. We would make use of six dimensions to help evaluate the shop. These six dimensions would be accuracy, completeness, consistency, timeline, validity, and uniqueness.

Accuracy would ask whether the information reflects what is in reality. For example, if five stocks were sold, then the number five was recorded on the dataset And if the phone number stored would be the exact same phone number the user would use. It refers to the data syntax you could argue.

Consistency would check if the information would agree across the entire system. A system without accuracy has no consistency.

Timelines would prefer if the information is useful in today’s context and if It would be up to date.

Validility would check whether or not the data would follow all of the shop rules. For example ranges, price being a valid number and so on.

Uniqueness will check whether the same real world occurrence Would appear once or more. In the context of if something happened, was it recorded twice. It would cause data inconsistency.

Making use of this information quality is really important since it would make our data trustworthy. If our data is inaccurate or incomplete or is just out of date, we cannot process it into valuable information since the decisions used with this information to apply knowledge and wisdom to this data would be inaccurate since the data is not correct. So validating data, storing it accurately and reliable would be very important at Leratu Home and Hardware

Catching it at the counter, not at month-end

A rule that fires while the customer is still standing there costs thirty seconds. The same error found at month-end costs an afternoon, and found after a decision has been made on it, it costs real money.

Error stops the save

Reserved for things that are definitely wrong and cannot be a deliberate exception.

  • A sale pointing at a product that does not exist
  • A selling price below the cost price
  • "On account" for a cash-only customer
  • Marketing consent ticked with no date recorded
  • A sale dated in the future

Warning asks, then records the answer

The record saves, but the person has to acknowledge it, and the acknowledgement is stored in the envelope.

  • Selling more than the recorded stock on hand
  • A margin under 10%
  • A customer going over their credit limit
  • A mobile number already on file for somebody else
  • A stock adjustment over 50 units

One of the most. important design decisions in the system would be having two levels of security. One would be warning and the other one would be errors.

An error would prevent a record from being saved when a rule has been broken in the way that the system cannot safely accept the transaction.

A warning, however, would identify something unusual that still might be legitimate.

making use of both a warning and an error would make the shop able to operate in an imperfect world that we live in today.

Let’s consider a few real scenarios. A damaged bag of cement might be sold at a discount by a trusted customer might not be allowed to exceed the credit limit temporarily, or the stock might not be present, although it has been booked on the system. These situations deserve attention, but automatically rejecting every one of them would prevent staff from doing their jobs. So with The use of data validation. Some of these transactions would look sketchy. For example, the broken cement bag sold for cheaper. The system would flag this, but this error should only be a warning, making it able to sell this bag of cement at a cheaper price, even though it broke the rules. But this is an imperfect world.

On the other hand, errors are still necessary. For example, what if someone would purchase something while their money goes out of their bank account, and then before it goes back into the business bank account, they use connection. Then they would lose their money, and the business bank account would not receive any money. In this transaction, while an error occurred in the middle of the transaction, this would cause the money just to plainly get lost. So, since it is sent but not received, the money is deducted from the customer’s bank account but not received. If this happens, a transaction needs to be re-rolled and an error needs to be occurred.

Using the errors and warnings would make it possible for the business to operate efficiently, to catch errors, but also be able to manage in real-world exceptions

Before choosing a software, the shop must first understand where some of its information currently comes from. So the business could record something on spreadsheets, invoices, supplier notes, accounting systems, or even writing down on paper. Mapping these resources would reveal what information exists, who maintains it, and how it moves through the business. Things can be recognized like the current validation being done. Without this overview, the business cannot know what system needs to be used to communicate. For example, you cannot use some fancy software when the users mainly make use of pen and paper

An experienced business owner could remember what customers paid late, which suppliers offer special arrangement, and how stock is kept for busy payments. This knowledge is valuable, but it creates a risk for the business. What if the owner becomes ill and takes leave or decides to sell the shop? All of this knowledge now is unavailable. This becomes a single point of failure for knowledge inside of the business. It makes the entire business hard to transfer to a new owner. That is why documenting all of this knowledge is very important and it would turn personal into experience to something that people in the business can reuse.

This is why the shop should establish a single source of truth. For example, document special customer needs, Techniques inside of the business used to make it run smoothly and efficiently, Same method of capturing the same data in the same format.

Before any software can be chosen, the owner should complete the data source of truth table for their own shop, knowing what is required in the shop and how information and knowledge can be carried over.

Imagine that there would be a busy afternoon at the shop. A customer would request a quote for building materials and accepts it to return later to collect the order. Without using any data reuse, staff would have to retype the customer’s detail each time, including their ID, product descriptions, quantity, price into the invoice. Every repeated entry creates an opportunity where a typo may occur, an incorrect price, or a disagreement between documents. With a structured system, the quote and invoice would be generated with the same underlying records.

Instead of the user going in and typing all of the things manually, the user would instead just validate and check that all of the data generated on the invoice would be correct. Workers can give more attention to correctness than speed, since the system does everything automatically for them. They just have to double-check it.

By using this system it also makes it easier to track errors. For example, if someone would just fill in a typo, it would be very difficult to trace where exactly the problem came from. But if there was An incorrect update in the database or some type of flaw in the program, it would be able to trace where the error came from.

Our value would not necessarily come from producing the document faster. It would come from producing it consistently, tracing it back to its source and reusing information accurate and consistent throughout the entire business.

Dashboards: what to put on one, and what to leave off

Most small-business dashboards fail the same way — they show everything that can be counted, so nobody looks at them twice. A dashboard is not a report. It is a short list of things worth interrupting the day for.

Scroll sideways to see the whole diagram.

The test for every tile on a dashboard

"If this number moved, what would I do differently today?" If there is no answer, the number belongs in a monthly report, not on the daily screen. Most dashboards fail this test on most of their tiles.

A dashboard and a report would serve different purposes. A dashboard is a short and action-oriented view of the business that helps the owner monitor conditions and decides what needs attention today and right now. A report is usually more detailed and produced periodically for review, comaparisson and investigation.

Data visualization must also match the question being asked. Coulomb charts work well for comparing value across days or months, especially when showing a change over time. Horizontal bar charts are useful when category labels are long or certain words. Using a donut chart, you can also show how data is divided among small number of categories. But it becomes difficult to interpret when it contains too many slices. Three-dimensional charts distorts visual components.

We must take note that charts can also be misleading without showing false numbers. Truncated axes exaggerates small changes by making their appearance look dramatic. Comparison an incomplete month with a completed month creates an unfair comparison. Averages can hide important details, such as an unusual large customer depth in the business

Exceptions are often the most immediately useful part of a dashboard. The demonstration third band presents a list of name records that needs attention. Rather than simplifying an exception count, knowing that five problems exist is less useful than knowing which five problems are effective and what needs to be done.

The dashboard summarizes today’s performance and reveal trends. While the report shows required action that needs to be taken.

Examples like turnovers, gross margin, stock turn, debtor pays and customer concentration

For a small business, gross margin can matter more than the turnover alone. High sales do not guarantee that the business is making enough money. For example, suppose the shop sells 100,000 Rand worth of cement and building materials in a month, with those goods costing R85,000 to purchase. It’s the gross profit is R15,000 and the gross margin is 15%. If the turnover increases to 120,000 but the cost raised to 108,000 gross profit falls to 12,000 Rand and the margin drops to 10%.

Customer concentration would also be very important and deserves a lot of attention. If one contractor accounts for 20% of the total sales, then most of your business relies on those transactions. If the customer would leave or anything significant might happen, it would have a huge effect on your business

The owner should instead not look at vanity matrics. So instead of chasing the highest numbers, the owner should instead try and chase the best decision at the specific time given the scenario and the context.

Keeping it: backups, retention and the stolen laptop

The question that decides everything else

If the shop laptop were stolen tonight, what would the business lose? For most small businesses running on spreadsheets, the honest answer is: everything except what is in the invoice book, and nobody would find out until they needed it.

Business information is valuable only if it remains available, protected and recoverable. A laptop containing every customer record, invoice and stock figure creates a serious risk if it gets stolen, damages, or just starts failing. The shop should keep multiple copies of its data, including at least one backup stored outside the premises. Backups should be tested by restoring them to confirm that the information can actually be recovered. An untested backup would only be a hoop, not a backup. The shop should establish regular backup schedules and periodically verify that both the records and the relationships remain usable within the system and the backups.

Cloud storage and on-prem-premise storage have the advantages and disadvantages. Cloud services can protect against the loss of equip ment at the shop and allow access for files from different locations. However, South African businesses must consider load shedding, mobile delta costs and unreliable internet connectivity. On-premises storage can allow access without the internet connection, but it would remain vulnerable to theft, physical damage, and power problems.

There should also be a data trail. For example, who changed this data? It would demonstrate records for old and new value, making investigation possible instead of relying on memory. So it would make people responsible but also help track changes. Together, these features would support accountability, portability, and recover the original system when the files become unavailable

What to do on Monday

Nothing on this page needs software to start.

  1. Write down where every fact enters the business

    The seven-row table above, for this shop. One page, half an hour. Everything else depends on it.

  2. Decide the single source of truth for each fact

    For stock, for price, for what a customer owes. One place each. Write down which.

  3. Agree the minimum you will capture for every sale

    Even in the invoice book. Date, who served, what was sold, what it cost, how it was paid.

  4. Count the stock properly once

    Any system you buy will inherit whatever figure you give it. Starting a new system on a June guess means paying for a system that is wrong on day one.

  5. Then, and only then, look at software
